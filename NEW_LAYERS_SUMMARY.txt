================================================================================
                          ARCHITECTURE FLOW
================================================================================

Raw Gmail
    ↓
[1] Input Normalization → NormalizedEmail {subject, from, body, links, date}
    ↓
[2] Recruitment Classification → YES/NO + confidence
    ↓
[3] Document Understanding ✨ → application_confirmation | assessment | interview | offer | rejection ...
    ↓
[4] Information Extraction → {company, role, salary, recruiter, date, links, ...}
    ↓
[5] Validation → Are facts valid? (confidence scores, issues)
    ↓
[6] Resolution ✨ → Multiple extractors? Pick winner
    ↓
[7] Identity Resolution ✨ → New application or merge with existing?
    ↓
[8] State Engine ✨ → Current state + history + validity
    ↓
[9] Timeline Engine → Convert to timeline events
    ↓
[10] Output Builder → ParsedApplication

RESULT: Perfect, mergeable, stateful application records

================================================================================
                          GUIDING QUESTIONS
================================================================================

A good architecture answers ONE question per layer:

1. What is this email? (Normalization)
2. Should I care about it? (Classification)
3. What TYPE of recruitment email? (Document Understanding) ✨
4. What facts can I extract? (Extraction)
5. Are those facts valid? (Validation)
6. Which facts are most trustworthy? (Resolution) ✨
7. Which application does this belong to? (Identity) ✨
8. What is the current state? (State Engine) ✨
9. How should user see history? (Timeline)
10. What structured output? (Builder)

Example 2: Salary Extraction Conflict

Three extractors suggest:
  A: $200k (confidence: 0.9, from: body_pattern)
  B: $200000 (confidence: 0.85, from: regex)
  C: $0.2M (confidence: 0.7, from: fallback)

WITHOUT Layer 6:
  Three different values in database
  
WITH Layer 6 (Resolution):
  A wins: $200k (confidence 0.9 is highest)
  Others noted as extractors but not stored

Example 3: Company Name Variations

Email says "Google" but domain is "google.com"
Email says "GOOG Inc" but domain suggests "Alphabet"

Layer 6 (Resolution) combines:
  - company_domain (highest priority)
  - email_body_pattern
  - consistency check
  Result: Canonical name, one confidence score
